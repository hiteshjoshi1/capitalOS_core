# Issue 154: Tests and CI: migrate an empty Postgres, Postgres test subset, production-like auth defaults, cross-user isolation

Issue: https://github.com/hiteshjoshi1/capitalOS_core/issues/154

## Objective
- CI proves the migration chain works: every migration applied to an empty Postgres 16, a re-run is a no-op, and the result matches a committed `migrations/schema.sql`.
- Code that branches on the dialect, and every GET route's SQL, runs on real Postgres in CI (`pytest -m postgres`).
- The backend suite runs like production: no auth bypass, no legacy NULL-owner rows; a missing user-scope clause fails a test.

## Architecture Decisions
- One runner: the CI job and `make db-schema-check` call `make db-migrate DB_CONTAINER=<throwaway>`, the same target the real stack uses. The throwaway instance reuses `docker-compose.isolated.yml` (own project/container/port/volume; pinned postgres image from the base file, no second pin). Ports: worktree 15600-15999, main checkout 15599; 5432-5434 refused.
- `migrations/schema.sql`: `pg_dump --schema-only --no-owner --no-privileges` with the version banner and the per-run `\restrict` key stripped. Regenerated by `make db-schema-update`; every new migration must commit it (CI fails otherwise).
- Postgres tests get a fresh copy of the migrated database per test (`CREATE DATABASE ... TEMPLATE`, dropped after), and the app is pointed at it through the existing `get_db` override. Skipped when `TEST_POSTGRES_URL` is unset (default SQLite run).
- Test auth: the `client` fixture signs in as user 1 (admin) with a real access token (`tests/auth_helpers.py`); `anon_client` sends no credentials. Rows inserted by tests carry their owner explicitly; the SQLite schema was not given a default owner (that would hide an app insert that forgets `user_id`).
- Cross-user isolation: every GET in the OpenAPI schema is called as user B before and after user A's data is written (through the Flex import, upload balance adapter and History backfill where those exist); B's answers must not change and must not contain A's sentinel strings. Shared routes are an allow-list with reasons (and must answer A and B identically); one skipped route (network relay). A positive-control list checks A's data reaches the routes. Runs on SQLite and on Postgres.

## Acceptance Criteria
- [x] CI job migrates an empty Postgres 16, re-runs (no-op), diffs against `schema.sql`, runs a Postgres subset.
- [x] Test defaults flipped (bypass off, legacy-null off); tests fixed with explicit fixtures.
- [x] Parametrised cross-user isolation test over every GET route, with an explicit shared allow-list.
- [x] CI fails on a broken migration or a missing scope clause (negative tests below).

## How To Test
- `make db-schema-check`: migrates, re-runs, diffs, then `pytest -m postgres` (9 tests).
- `make test-backend`: full SQLite suite, Postgres tests skipped.
- Negative: add `migrations/099_x.sql` with invalid SQL -> `db-migrate` fails; with valid DDL -> schema diff fails. Remove a user-scope clause from `/crypto/tokens` -> the isolation test fails on SQLite and Postgres naming the route and the leaked strings.
